# Tests and scores

A message is spam at 5 points and rejected at 15. Each test below adds or removes points; the result lists the ones that fired. A `rejectThreshold` below `threshold` rejects only spam.

Change the thresholds with `threshold` and `rejectThreshold`. Change points with `scores`, either by setting key (`scores: {deceptiveLink: 4}`) or by test name, which fixes that test's points (`scores: {FROM_NAME_BRAND: 4}`).


## Classifier

| Test                      | Points        | Meaning                                                                                                                                                                                                                                                                                                                                            |
| ------------------------- | ------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BAYES_00` to `BAYES_999` | -2.5 to +6.25 | The classifier's spam probability, on a log-odds scale: 2.4 points at 90%, 5 at 99% and 6.25 at 99.9%, so the classifier marks spam on its own only when it is at least 99% sure. The name gives the band: `BAYES_999` is 99.9% or more, `BAYES_99` 99% to 99.9%, `BAYES_50` 40% to 60%. Setting keys `bayesHam` and `bayesSpam` set the two ends. |

| `MIME_TOO_COMPLEX`      |      6 | `mimeTooComplex`                         | Over 1000 MIME parts, or a part header over 1 MB, also in an attached message, or an attached message that cannot be read; later parts unread |

Only these two limits of the MIME parser give `MIME_TOO_COMPLEX`, and an attached message the parser fails on; any other parser error fails the scan, and the servers defer the message, as earlier versions did. A message with too many parts is read up to the 990th line that may start one (`--`), or, when attached messages inline make the parts, its first half, then a quarter, until it can be read. A message whose own header is too large is read with that header cut down (lines of at most 998 characters, fields of at most 8 KB, and only the fields that say who sent it and how if it is still over 512 KB), so its sender still counts; when the header of a later part is too large, its first megabyte is read. ClamAV reads it whole. Only `ALLOWLISTED` and `TRUTH_SOURCE` can offset it: other credits (Bayes ham, SPF, DKIM, DMARC, ARC, the language model's ham) count for nothing on it, as what was not read cannot be vouched for.

## Authentication

Needs the client's IP address and `authentication: true`.

| Test           | Points | Setting key (in `authentication.weights`) |
| -------------- | -----: | ----------------------------------------- |
| `SPF_PASS`     |   -0.5 | `spfPass`                                 |
| `SPF_FAIL`     |      2 | `spfFail`                                 |
| `SPF_SOFTFAIL` |      1 | `spfSoftfail`                             |
| `DKIM_PASS`    |   -0.5 | `dkimPass`                                |
| `DKIM_FAIL`    |      1 | `dkimFail`                                |
| `DMARC_PASS`   |   -1.5 | `dmarcPass`                               |
| `DMARC_FAIL`   |    3.5 | `dmarcFail` (policy quarantine or reject) |
| `DMARC_FAIL`   |      1 | `dmarcFailNone` (policy none)             |
| `ARC_PASS`     |   -0.5 | `arcPass`                                 |
| `ARC_FAIL`     |      1 | `arcFail`                                 |

The DMARC record is read as RFC 7489 reads it, whatever its spacing and case (`p= None` is `none`, `adkim=S` is strict), and strict alignment is enforced: under `adkim=s` only a signature of the From domain itself aligns, and under `aspf=s` only an SPF pass of it, so a message that meets only relaxed alignment fails DMARC. A message without exactly one From address (two addresses, two From fields, a group, an address only in an encoded word, or no From at all), whose DMARC mailauth does not check, fails DMARC with the policy unknown, as RFC 7489 (section 6.6.1) allows.

A DMARC failure scores by the domain's policy: in full when the domain asks for failures to be quarantined or rejected, or the policy is not known, and SPF failing as well adds nothing more (`SPF_FAIL` and `SPF_SOFTFAIL` are left out), as DMARC already counts it. When the policy is `none`, the domain does not stand behind its failures, so `DMARC_FAIL` is small, but SPF's points count on top of it: a domain with policy `none` is never easier to spoof than one without DMARC (SPF failing with `-all`: 2 points without DMARC, 3 with policy `none`, 3.5 with quarantine or reject). A message forwarded without SRS, with a footer added that breaks its signature, gets 3.5 points at most, not 5.5.

A DKIM signature of only the start of the body (a body length, `l=`, shorter than the body: anyone can add text after it) earns no `DKIM_PASS`, and a DMARC pass that rests on one alone, without SPF aligned, no `DMARC_PASS`.

A forwarder, such as a mailing list, can vouch for what it received with an ARC seal. Anyone can seal a message, so a seal counts only from a forwarder you name in `authentication.trustedArcSealers` (a domain covers its subdomains), and only when the newest ARC set is sealed by that domain (its ARC-Seal and ARC-Message-Signature of the same domain) and the results it sealed show the message passed when it got it: DMARC for the From domain, or DKIM or SPF of a domain with the same registrable domain. Such a message (`authentication.arc.trusted`) gets `ARC_PASS` and no points for failing SPF, DKIM or DMARC, and is not `SELF_SPOOF` (a list member writing to a list of their own domain); any other ARC pass gets nothing, and an untrusted or failed seal still gets `SELF_SPOOF`. Results passed in `authenticationResults` trust no forwarder.

```js
new SpamScanner({authentication: {trustedArcSealers: ['lists.example.org']}});
```
